# 实现缺口与需要补充的研究材料

实现过程中发现、研究文档（campus-auth-research，“doc NN”）还没有覆盖的地方。每条都写明缺什么、出自哪一篇，以及实现目前的保守做法。补齐后可以提高对应 driver 的验证程度。

## 安朗 UDP（`gswifi-anlang`）

1. **登录拒绝没有原因码**（doc 04.5）：只知道“偏移 20 为 0 表示拒绝”。目前任何拒绝都按密码错误停止（`retry_on_reject = true` 恢复固件的无限重试），分不清“已在线”“服务名错”“服务器忙”。**最影响实际使用**，和第 8 条一起看。
2. **发现应答**（doc 04.1/04.7）：应答 op 未知；只确认客户端取第一个 `0x0c` 后两字节起的 4 字节，不确定是 `0c 06 ip4` TLV；应答来自 1.1.1.8 还是真实服务器、校园网关是否拦截 1.1.1.8 都未知。固件把 IP 转文本时似乎会丢掉十位的 0（200→"20"），待动态确认；实现直接用原始字节。
3. **服务/登录/心跳应答的 op 码**未知，实现不检查。
4. **应答摘要**：服务器是否真的计算 MD5？默认 `response_check = "strict"` 丢弃摘要错的应答，`"firmware"` 照单全收。需要抓包。
5. **应答长度**：固件忽略登录/心跳应答的长度字节、接受最多 4095 字节；严格模式要求 18..=127 且长度一致。需要真实应答长度。
6. **登录应答 23+n 之后的字段**：有没有服务器消息（GBK？）或下发的心跳间隔？目前写死 20 s。
7. **会话长度上限**：超过 39 字节放不进 127 字节心跳，实现按 Fatal 停止；会话含 NUL 时按固件截断，未验证（doc 04.6）。
8. **没有下线报文**，服务器端会话过期时间未知。重启或换 IP 后重新登录可能收到“已在线”，按第 1 条会直接停止。
9. **心跳应答**：被踢/过期有没有单独的标志？服务器是否校验计数器、是否接受同一计数器的重发？
10. **含义不明的常量**：发现/服务查询里的 TLV 8 `00 01 02 03 04`、登录里的 TLV 14 `00`、心跳的 TLV 42–47（全 0）、版本串 `4.2.0`，是否因学校而异？
11. **服务应答**：能否列出多个服务？固件只读偏移 18 的字段；缺失时固件要求手动输入，实现停止并提示配置 `service`。
12. **字符编码**：用户名/密码/服务名用 GBK 还是 UTF-8？目前按配置原样发送（UTF-8），服务名按 GBK 显示。
13. **应答源地址/端口**未验证；固件的失败计数从不清零，可能是固件缺陷。
14. **安朗 802.1X**（doc 22.2/25.5）：只恢复了用户名格式，Success 之后的行为未知。

以上第 2、3 条及计时（发现 1 次、登录 3 次间隔 5 s、心跳 20 s/失败 1 s 重发/累计 3 次退出、每 10 轮 ifup）是从 atclient 反汇编静态读出的，未动态确认。

## Dr.com（`gswifi-drcom`）

1. **Dogcom 登录**（doc 03 §3.2）：ror 密码长度不是 8/9 时的填充规则（只给了“ror base 338”）；JLU 布局与 `60 a2` 尾部及何时启用（“多次 login 失败后尝试 JLU”）；85:97 和 150:162 是否会非零；缺 Dogcom 自身的登录金样本。
2. **keepalive2**（doc 03 §3.4）：type1 是否带尾部（目前按表填 0）；哪些应答长度/类型有效；计数器是否从 0 开始、重新登录是否清零。
3. **PPPoE**（doc 03 §3.5）：Dogcom login96 的 32:96 字节（目前发 0；GS control96 会填充并轮换，像另一种客户端）；login96 应答格式（借用了 doc 30.2 的分类）；挑战应答首字节（要求 07）；挑战+登录是否周期重复（GS P 回放显示会）。
4. **下线**：Dogcom 下线报文完全没有规格，GS 只有 `01 01` 下线挑战。
5. **计时与重试**：Dogcom 重试上限、重新登录前允许的 keepalive 失败次数、退避（doc 03 §3.2 只说失败会“累计”）。
6. **GS D/P/Pt 在线阶段**：phase 447270 的完整可达图；control3 何时发送；P 在线 tick 的内容；首次失败后隐藏的 JLU 回退（doc 30.7）；DrMode5 路径；DrMode4 需要 core 支持 TCP 动作。
7. **GS X**：真实 EAP 交换和 1000 字节帧。
8. **GS Pt**：244 字节报文体的独立编解码。
9. **错误码 21**：服务器可变文本的偏移（doc 30.7）。
10. **profile 来源**：0x20/0x01/0x01、OS 6.2.9200、`DrCOM\0\x0f\x27\x02` 是 GS 常量还是配置；各学校真实的 AUTH_VERSION、KEEP_ALIVE_VERSION、pppoe_flag。
11. **验证**：任一 Dogcom 模式的实验室或实网完整会话抓包（可把等级提到 lab-tested 以上）。

新发现：GS D 版 342 字节登录体现在有独立编码器，可逐字节重建全部 6 个 D 回放帧。与 doc 03 的 Dogcom 登录有三处不同：checksum1 为 `MD5(p[0:97])`、不带 `14 00 07 0b` 后缀；不计算 checksum2（`01 26 07 11 00 00` 保持字面值）；尾部是整个报文体的 check16。

## H3C iNode 802.1X（`gswifi-inode`）

1. **BF 保活**（doc 25.5）：AuthType 1 会话实际发什么——key 和 echoNo 初值、0x447278/0x44735c 的条件、服务器是否需要。目前不发保活。
2. **在线查询**（doc 22.4）：UploadIP/UploadVer 是否也作用于在线应答；没有版本时发什么；服务器之后会不会再发挑战；多久查一次。实现按 GS 原地应答、保持在线。
3. **原始版本应答 0x41007c**（doc 22.4）：哪些请求类型触发；AuthType 1 下 Notification(2) 和 type 10 怎么处理。目前只导出构造函数。
4. **StartMode**（doc 21.1/21.3）：AuthType 1 的 StartMode 1（会加锐捷 Start 扩展）；模式 0/3 的 Start 目的地址轮换；PktType 的影响。目前拒绝 StartMode 1/2。
5. **“User name”自动切换赛尔**（doc 21.2）是否适用于 AuthType 1。
6. **密码辅助函数**（doc 13.4、02.7）：0x41ba24 和 0x40cdd4 在哪里使用；“secure”变体。
7. **inode-gs.dat** 在 802.1X 分支是否用到（doc 13.9）。
8. **VIF 尾部** 256 字节的含义（doc 13.3）。
9. **IP 为 0.0.0.0 时的 Identity**（doc 22.3）：DhcpMode 1/3 在获取地址前 GS 发什么。
10. **nonce**（doc 13.3）：服务器是否检查新鲜度。原程序用 time×rand；driver 不能读时钟，默认取 `MD5("gswifi-inode"‖mac‖user)[..4]`，整个会话不变。

## H3C Portal（`gswifi-h3c-portal`）

1. **属性 113**（doc 13.7 与 29.3 矛盾）：登录和 104 都读全局 0x44726c，GS 初始化时存的是 `time(NULL)`（0x40b84e），doc 13.7 说的“心跳参数”可能有误。默认仍为 30 以匹配向量。
2. **serial**（doc 29.1）：GS 初始化时用 `htons(rand())`（0x40b83c）。每轮是否重新生成？服务器是否回显或校验？
3. **111 信息属性**（doc 23.1）：哪些属性会更新 Portal IP 或端口。
4. **服务器认证码**（doc 29.1）：真实服务器是否用 "hello" 封包？（`verify_authenticator` 默认关闭）
5. **105 处理**（doc 29.2/29.4）：109 缺失或为 0（计时器 0）的含义；是否每个 104 都有 105；怎样判断会话丢失。
6. **未处理的类型**（doc 29.2/29.7）：100..123 中其他消息的含义，尤其 103（强制下线？）。
7. **属性 115** 的编码（假定 GBK）及是否带错误码。
8. **ARP 帧**（doc 29.4）：在线状态会发 ARP 帧，这里没有发。
9. **下线长度缺陷**（doc 29.3）：多出的 2 字节到底是什么；服务器是否接受 4 字节值（`logoff_session_quirk` 复现固件行为）。
10. **发现计时**（doc 29.4）：计数 1 不重新上定时器，假定 8 s。
11. **MaxFail 与重启**（doc 29.4）：重启等待后重试只在 harness 中见过；MaxFail 如何作用。
12. **没有 VIF 时**（doc 22.5）：属性 33 和 101 的内容；目前拒绝启动。
13. **本地端口 50200**（doc 23.1）是否也接收。
14. **服务器端口**（doc 29.1）：真实目的端口怎样从发现结果得到。
15. **属性 131**（doc 29.5）：每个 104 是否重新计算；校验失败时是否仍发 122。
16. **服务器头第 2 字节**（doc 29.2）：接收向量中为 1、会话中为 0，含义未知。
17. **心跳间隔**（doc 29.4）：10 s 是写死的还是来自 EchoInterval？

## 未实现的方式

- **NetKeeper/闪讯/SRun 等定制 PPPoE**（doc 12）：本次没有实现。研究包里没有任何 PPP 账号派生的黄金向量（`reference/*.py`、`vectors.json` 都没有，相关 claim PPP-NK 为 F/H 级），doc 12.4 也说明完整的 MD5 等价性没有动态核对。pppd 里有 doc 12 没提到的 `{SRUN3}`（0x271d4）、`{SRUN2}`（0x271e0）字符串。
- **云南/湖北网页 Portal**（doc 05）：没有派生算法的黄金向量，doc 05 标明“全字节算法未完成”。另外湖北模式映射不一致：LuCI 把 `usecapture` 0 标为 “hubei mac new”、1 标为 “hubei mac old”，而 `/usr/bin/hubei-service.sh` 实际 0 运行 `hubei_mac_web_old`、1 运行 `hubei_mac_web_new`、2 运行 Android；doc 01.3 与脚本一致。
- **Portal Relay、网页插件**（doc 06）：依赖私有 Netlink 材料和插件包，未实现。
- **固件的私有内核模块**（doc 16、cleanroom/10）：`xt_ob`（改包/注入，mode 1-6）、`dpimark`（DPI 流分类 + `rule_host8.dat` 规则库）、`xt_gttl`、`xt_IPID`、`xt_dumphelper` 没有移植。它们依赖私有 skb 布局和内核 ABI，不能跨内核加载，语义也未闭合；doc 27.6 明确建议第一版不要复刻 `xt_ob` 的低 TTL 附加包和伪分片。`gswifi-protect` 用标准 nftables 覆盖其中可移植的部分（TTL/IPID/时间戳/DSCP/ICMP/端口/DNS）。
- **双人格多出口（固件 mode 8/9）**：macvlan 双 WAN、按出口分别设 TTL/IPID/DHCP 指纹、`hijack-gate`、策略路由分流。doc 27.5 要求每个出口有独立的认证会话、地址、DNS 和故障策略；本版只支持单一人格，多出口列为后续。
- **收费中继 / SSR 隧道 / 配置分发**（doc 08）：不实现，也不打算实现。

## 防共享检测（`gswifi-protect`）

已实现并用真正的 `nft` 校验过 16 种规则变体；以下是还缺的东西。

| 缺失 | 类型 | 说明 / 出处 |
|---|---|---|
| 真实校园网的检测口径 | 验证 | 没有任何一所学校的实测：哪些特征真的被检测、改完之后是否还会被判共享，全部未知。当前只能说"出口报文的这些字段被统一了"，**不能说"能过检测"** |
| 流量分载（offload）下的有效性 | 行为 | 软/硬件 offload 时只有头几个报文经过 nftables，TTL/IPID 改写基本失效（doc 26.5）。需要在目标设备上测，并决定是否在启用时自动关 offload |
| GRO 导致的 IPID 重叠 | 行为 | 开 GRO 时合并报文在出口重新分段，各段 IPID 由内核依次加一，可能与下一个报文的 IPID 重叠。原固件在内核模块里按分段数步进，nftables 做不到（doc 26.5） |
| IPID 桶策略 | 字段 | 原实现按目的地址尾两字节分 65536 个桶、两套计数（doc 26.5），这里用的是单个全局递增计数。哪种更像真实主机未验证 |
| 分片语义 | 字段 | 原 `xt_IPID` 会覆盖整个 fragment 字段（含 MF/offset），可能改变重组语义；这里只改非分片报文的 ID。差异已记录，未做对照验收 |
| TCP 栈参数 | 字段 | doc 4 人格矩阵里的 `tcp_rmem`/`wmem` 分档没有移植（随 RAM 变化，且属于性能参数）。窗口大小也是指纹的一部分 |
| DHCP 指纹 | 字段 | 固件按人格发不同的 hostname / Vendor Class / 参数请求列表（cleanroom/06 §9）。这里没做，`gswifi` 不管 DHCP 客户端 |
| NTP 行为 | 行为 | 固件 PC 人格同步 `time.windows.com`、手机人格不同步（分析文档 §4）。这里只有可选的 LAN 123 接管，没有按人格改路由器自己的授时行为 |
| 验收矩阵 | 测试 | doc 27.7 的 netns 拓扑（client → router → server，两端抓包比对）没有搭。目前只验证了规则能被 `nft` 接受、能加载、重载幂等、观察模式不改包；**没有验证改写后的报文在接收端是什么样** |
| IPv6 | 范围 | 只做了 Hop Limit 统一和整段阻断两种。IPv6 通常每台设备一个地址，要真正隐藏设备数需要更多设计（doc 26.9） |
| QUIC / DoH / DoT | 范围 | 各有各的路径，当前策略完全不覆盖；过滤 AAAA 不等于阻断 IPv6，拦 UDP53 也不等于控制住 DNS（doc 26.9） |

## 运行时/工程

- 只有 `gswifi-link` 的 UDP 事件循环做过回环集成测试；pcap 收发 802.1X 没有在真实网卡上测试（mentorust 用的是同一套 pcap 参数）。
- 用静态编译的 `gswifi` 二进制在 OpenWrt 24.10 容器里跑过 `protect install/status/uninstall` 全流程，查出并修掉两个只有真机才暴露的问题：(1) 24.10 的 dnsmasq 不认旧写法 `filter-aaaa`，上游 2.87 起是 `filter-AAAA`（更老的、带 OpenWrt 私有补丁的 dnsmasq 会在 `--test` 时拒绝，片段不会生效）；(2) fw4 把 `/etc/nftables.d/*.nft` 包含在 `table inet fw4 { }` **内部**，顶层 `table` 声明放进去会让防火墙下次重启时整体加载失败，所以规则文件默认改放 `/etc/gswifi/protect.nft`，由 OpenWrt 包注册为 `ruleset-post` 位置的 include。`apply` 也改成两阶段：全部校验通过才提交，任何一步不过就把文件恢复原状。
- `gswifi-protect` 生成的规则在 OpenWrt 24.10 容器（nft 1.1.1、内核 7.2）里验证过：16 种变体全部通过 `nft -c`，`enforce` 能加载、重复加载幂等（计数器不翻倍）、切 `observe` 后没有 nat 链、`uninstall` 后表被删干净。没有在真实路由器和校园网上跑过。
- OpenWrt 包和 LuCI 已完成，在 23.05/24.10/25.12 官方 rootfs 容器里装过、测过；procd 实际运行只在 aarch64 24.10 容器里测过（x86 容器没有 procd）。两个 SDK Makefile（`openwrt/*/Makefile`）没有在 OpenWrt SDK 里编译过，发布包不走它们。
- 没有在真实路由器硬件上跑过。armv7 包只验证了"装到别的 CPU 家族会被拒绝"，没有在 armv7 上实际运行。
- mipsel（MT7621）：CI 里是实验性任务，能编出 3.0 MB 静态二进制并在 qemu 里运行；没有 mipsel 的 ipk，没有在真 MT7621 上跑过。用的 cross 镜像是 musl 1.1.24（32 位 `time_t`）。
- 配置错误目前和"网卡不存在"共用退出码 1，systemd 单元会每 30 秒重试一次错误配置（procd 最多重试 5 次）。计划给配置错误单独的退出码（如 78），本轮没有做。
- NetKeeper 拨号用户名没有接入 netifd/pppd，网页上只有计算器。
- 23.05 的 ucode 对 null 调用 `obj?.method()` 会报错，`openwrt/` 里已用辅助函数绕开；以后写 ucode 要注意。
- CI 只在本机用 Docker 复现过；矩阵连线、artifact 传递、Release 发布和权限只有推到 GitHub 后才能验证。
